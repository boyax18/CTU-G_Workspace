## Implemented flow and errors

The catalogue contains 13 numbered main steps and step-labelled error rows in the WF-01.01 format. Both roles share the existing /api/v1/auth/register/ and verification/verify/resend/cancel routes. Instructor OTP clients use requested_role=Instructor in the OTP route query for presentation/error context; the encrypted stage role, never that query, determines account creation. No endpoint/entity was added to the application.

Instructor conflict text before and after OTP:

> We can't continue this registration. This Staff ID or email is already registered, or a registration with it is already in progress. We did not send a verification code for this attempt.

The final sentence is exactly owner-stated. It never identifies which field conflicts. Initial/foreign-staged conflicts generate no OTP; final conflicts generate no new code and create no partial account/profile. Same-browser valid ownership returns existing_verification, no conflict message and no new send, even when the new form differs; the original details remain immutable. Unrelated Instructor profile duplicate-key errors now remain genuine 503 failures, rather than being mislabeled as identity conflicts. Student's error mapping/wording is preserved.

Four conflict action states: Log in uses /#login; Reset your password links /forgot-password only when the same backend feature flag is true, otherwise displays “Password reset is not available right now. Please contact support.”; Continue your registration is unavailable without original-browser possession (normal owned resume already continues directly); Contact support uses a configured safe public URL/email or “Contact the School Admin office.” There is no hard-coded official address and no identity-based resume lookup.

WORKSPACE_REGISTRATION_SUPPORT_CONTACT defaults to empty and may contain a public http(s) URL or email/mailto address. Invalid schemes, line breaks and credential-bearing URLs fall back safely. Responses expose only this public setting and the existing recovery flag, never SMTP credentials. Safe options are included only in Instructor responses; Student's approved response shape is retained. Recipient display is returned only for the cookie-owned Instructor stage, never for a conflict or missing foreign session.

Instructor shows remaining wrong-code attempts; expired code offers Send a new code with resend countdown; exhaustion explains cancellation or fixed expiry as retry paths. Wrong email? Go back explicitly cancels before returning to the Staff ID form. Delivery failure is honest, clears an uncertain code and retains encrypted staging for bounded resend. Successful OTP confirmation explains School Admin review.

Accepted abuse/default limits are documented in D-14: existing registration IP 5/min and 30/day; OTP/status IP 30/min and 200/day; those respective budgets also per keyed Staff ID/email for Instructor; DB constraints cap one live stage per ID/email; fixed 30-minute stage expiry is not extended by resends. Current DRF/cache throttling is best effort in the configured cache backend; a shared multiworker cache/global deployment contract is not claimed. Temporary first-claim blocking until cancellation/expiry remains an accepted risk. The existing purge worker removes only expired temporary stages every 60 seconds; immediate expiry refusal does not depend on it.
