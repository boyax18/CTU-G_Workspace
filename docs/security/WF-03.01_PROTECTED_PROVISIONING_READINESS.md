## 3. D-102 — P3B compatibility with the v2.2 governance extension

v2.2 binds 13 defaults to Technical Super Admin:
- the 6 composition codes;
- the extension set `E` = `access_control.role_assignments.ordinary.manage` (v2.1, index 98),
  `access_control.school_access.inspect` (index 97) and `access_control.audit.school.read` (index 102);
- `access_control.diagnostics.read`, excluded from `E` unless separately approved;
- `accounts.profile.self.read`, `accounts.profile.self.update` and
  `accounts.authentication_events.governance.read`. These three are outside D-102. The last is a WF-12
  event-source code that stays dormant until WF-12.01/12.02 approve it.

Requirements:
1. **Single source:** the definitions come only from `validation_v2_2.validate_catalogue()`, which validates
   v2.0 and v2.1 first. Every created permission row matches the v2.2 definition: service
   `access_control`, `permission_name`, `module_name`, `action_name` and `description`.
2. **Provisioning (`_ensure_governance`):** create each approved code of `E` and exactly one active binding
   on the active Technical Super Admin role, with `granted_by` set to the operator. Never bind it to Admin
   or any other role.
3. **Receipts:** one `framework.permission.create` and one `framework.role_binding.create` per code. They
   must be field-exact: no target, no prior value, the exact `new_value` including `role_permission_id`, and
   reason `permission_change`. They must come from a staff superuser who holds no Workspace role, and be
   ordered role receipt < all permission receipts < all binding receipts, all after the registration P4
   activation. They may be part of the first grant or a later extension pair.
4. **P3B (`_governed_governance_profile`):** accept only the approved subset `S ⊆ E`, fixed by the
   approval, with receipt counts `1 + (6 + |S|) + (6 + |S|)`. Refuse any partial, foreign, inactive,
   Admin-bound, altered or unproven extension row, and any missing, duplicate, forged or reordered receipt.
5. **`_assert_effective_permissions`:** classify the codes of `S` like the governance codes.
6. **Unchanged:** `_assert_no_governance_profile` (D-85 compensation refusal), the P4 rollback scope, the
   registration-review and WF-02.05 school-account checks, the lock order (`select_for_update` on services,
   permissions, bindings, assignments and receipts) and the protected-writer refusal.
7. **Tests (disposable MySQL only):** acceptance of every approved `S`; each tamper above; D-85
   refusals unchanged; P4 compensation refused while effective; the existing D-85, D-89 and D-103 suites.

## 4. D-93/D-95 — Django Superuser procedure on the development database

Present and tested in the disposable database:
- password re-authentication through Django's hasher;
- the `WORKSPACE_ROLE_CONFIGURATION_OPERATORS` allowlist (unset);
- an operator that is staff + superuser + active + Approved with no Workspace role;
- TTY-only console input and an exact per-operation confirmation;
- `writer_atomic` READ COMMITTED with the WF-02.05 lock order;
- append-only `framework.*` receipts;
- a session epoch bump on role assign/revoke;
- protected-writer refusal;
- the last effective Technical Super Admin is never removed;
- full rollback on failure.

Required before development-database use:
1. A development-target branch in `_require_approved_target`, equivalent to P1's target checks:
   `config.settings`, DEBUG on, one database alias, MySQL on loopback, NAME `ctug_workspace`,
   `SELECT DATABASE()` equal, READ COMMITTED, review flags off and no unexpected route. It replaces
   `DEVELOPMENT_DATABASE_APPROVED`.
2. A database-bound confirmation: `ctug_workspace:WF-03.01:<operation>:<account_id>`.
3. One named operator per real person in an owner-controlled local setting outside the repository, never
   stored with credentials. D-95 evidence (who authorized, and when) goes in the signed operational record,
   because `audit.py` cannot store it.
4. A verified backup before the first grant: consistent `mysqldump --single-transaction` with routines and
   triggers, kept outside the repository, digest recorded, restore rehearsed as in WF-02.05 stage 3C.
5. Transactional provisioning of the role, permissions (v2.2 via D-102), bindings and receipts in one
   transaction, or nothing.
6. Session revocation of the target through the existing epoch bump, verified after the grant.
7. Recovery: the last-Technical-Super-Admin protection stays, and D-99 must be decided before the first
   real grant.
8. Cosmetic: the refusal text still names D-85, which is now implemented; change it together with item 1.

Tests: development-target acceptance and every refusal (wrong settings, DEBUG off, other database name,
remote host, extra alias, isolation level, flags on, mounted route); the database-bound confirmation;
operator designation; the existing WF-03.01, D-85, D-89 and D-103 suites.
